## 1. 系统愿景与产品定位 (Vision & Positioning)

### 1.1 项目愿景
**rs-gate** 是一款采用 Rust 构建的高性能、低资源占用、单二进制交付的企业级内部大模型网关。它作为企业内部所有 AI 业务系统与上游模型提供商（如 OpenAI、Azure OpenAI、DeepSeek、Claude、本地 Ollama/vLLM 等）之间的统一接入中枢与安全防线，解决企业大模型应用落地过程中的**凭据泄露风险**、**调用配额无序**、**并发冲击雪崩**、**账单计量混乱**以及**运维部署沉重**等核心痛点。

### 1.2 核心价值主张 (Core Value Propositions)
1. **极致轻量，单二进制开箱即用 (Single Binary Delivery)**：后端核心网关逻辑与前端 Web 控制台资源深度融合编译为单个可执行文件，无须配置 Node.js、Redis、MySQL 等外部服务依赖，秒级启动。
2. **极速透明，零缓冲流式代理 (Low-Latency SSE Passthrough)**：深度优化基于 Tokio 和 Hyper/Axum 的异步数据流管道，对 Server-Sent Events (SSE) 实施逐 Chunk 实时透传，网关引入的额外首字延迟（TTFT，Time to First Token）控制在 2ms 以内。
3. **安全可控，细粒度流控隔离 (Multi-tenant Key & Rate Limiting)**：企业内部分发虚拟 API Key，物理隔离上游真实凭据；支持基于 RPM（每分钟请求数）、TPM（每分钟 Token 数）、最大并发数以及日/月配额的多维度硬性阻断与软性告警。
4. **透明审计，异步持久化与自升迁 (Async Audit & WAL Storage)**：基于 SQLite WAL 高性能并发模式，采用后台非阻塞异步通道记录完整调用链指标与 Token 消耗，保证主代理流水线绝对零延迟损耗。

## 2. 需求功能矩阵 (Feature Matrix)

特性优先级定义：
- **P0 (Must-Have)**：MVP 核心基石，必须在 Milestone 1~3 全部完成交付并具备生产可用性。
- **P1 (Should-Have)**：生产就绪与健壮性保障，在 Milestone 4~5 完整实施并经过压力测试验证。
- **P2 (Nice-to-Have)**：进阶与扩展特性，在核心体系稳定后作为演进增强项。

| 编号 | 特性名称 | 优先级 | 功能描述与规范 | 验收指标 / 衡量标准 |
| :--- | :--- | :---: | :--- | :--- |
| **GW-01** | OpenAI 兼容聊天接口代理 | **P0** | 完全兼容 `/v1/chat/completions` 标准协议，支持非流式（JSON）与流式（SSE `stream: true`）请求无缝代理。 | 100% 通过 OpenAI 官方 Python/Node.js SDK 标准测试用例调用。 |
| **GW-02** | SSE 低延迟非阻塞流式中继 | **P0** | 针对流式响应，采用异步管道边读边写，严禁中间全量缓冲，对 `data: {...}` 事件帧及 `data: [DONE]` 实施零拷贝透传。 | 网关引入的额外首字延迟 (TTFT Overhead) $\le 2\text{ms}$，端到端 chunk 抖动 $< 1\text{ms}$。 |
| **GW-03** | 模型元数据列表代理 | **P0** | 兼容 `/v1/models` 端点，根据当前租户所分配的权限，动态返回其被允许访问的模型清单。 | 客户端调用 `/v1/models` 仅能看见授权的模型切片，格式与 OpenAI 规范完全一致。 |
| **GW-04** | 流式 Token 实时提取与计量 | **P0** | 实时解析 SSE 尾部携带的 `usage` chunk（兼容 `stream_options.include_usage`），准确记录 Prompt 与 Completion Token 数。 | 审计记录的 Token 消耗与上游实际返回账单 100% 吻合。 |
| **GW-05** | 智能模型路由与映射 (Alias) | **P0** | 支持客户端请求逻辑模型名（如 `gpt-4o-internal`）与上游真实模型名（如 `gpt-4o-2024-08-06` 或 Azure 部署名）的透明映射。 | 请求路由至目标提供商，客户端无须感知上游真实模型部署标识。 |
| **GW-06** | 协议头清洗与链路透传 | **P0** | 剥离上游或下游敏感的 Hop-by-hop 头信息；注入统一的请求链路跟踪 ID (`x-request-id`)，透传客户端真实 IP (`X-Forwarded-For`)。 | 确保下游与网关的日志具有统一的 `x-request-id` 进行串联追踪。 |
| **GW-07** | 向量嵌入接口代理 (Embeddings) | **P1** | 兼容 `/v1/embeddings` 标准协议，支持批量输入文本的向量化请求代理与 Token 计数。 | 支持最大 2048 长度的批处理请求，正确统计 Prompt Token。 |
| **GW-08** | 上游健康探测与故障熔断降级 | **P1** | 周期性对多上游节点进行心跳探测；当主节点连续出现 5xx 或超时故障时，触发断路器自动降级至备用提供商。 | 主节点故障时，在 3 次连续失败后自动 failover 至备用上游，避免客户端报 502。 |
| **GW-09** | 客户端主动断开连接感知 | **P1** | 当客户端提前 abort/取消 HTTP 连接时，网关立即捕获并中断对上游模型的长连接，停止产生无意义的计算与计费。 | 客户端断连后 100ms 内向 upstream 发出 abort，杜绝 Token 浪费。 |
| **GW-10** | 本地分词器兜底估算 (Tokenizer) | **P2** | 针对未返回 `usage` 数据的上游流式响应，引入嵌入式分词引擎（如 `tiktoken-rs`）在网关侧进行 Token 估算补偿。 | 当缺少上游 usage 块时，Token 误差率控制在 $\pm 5\%$ 以内。 |
| **GW-11** | 权重负载均衡 (Load Balancing) | **P2** | 支持同一模型配置多个后端提供商实例，按配置的权重（Weighted Round-Robin）进行流量均匀分发。 | 能够依据节点健康状态动态调整权重分发比例。 |

### 2.2 流控与安全领域 (Security & Limiting)

| 编号 | 特性名称 | 优先级 | 功能描述与规范 | 验收指标 / 衡量标准 |
| :--- | :--- | :---: | :--- | :--- |
| **SEC-01** | 网关虚拟 API Key 鉴权 | **P0** | 客户端必须携带 `Authorization: Bearer <rs-gate-sk-xxx>`；数据库仅保存 Key 的加盐 Hash 摘要，禁止明文持久化。 | 非法或已撤销 Key 立即拦截并返回标准 401 Unauthorized 错误。 |
| **SEC-02** | 上游真实凭据物理隔离与保护 | **P0** | 真实的 Provider API Key 统一由网关注册和加密托管，客户端永远无法获取、探测到任何上游真实凭据。 | 网关下行响应中严格过滤所有涉及上游鉴权信息的响应头与字段。 |
| **SEC-03** | 高性能内存令牌桶限流 (RPM) | **P0** | 针对每个虚拟 Key 支持配置单独的 RPM（每分钟请求数）限制；基于无锁/原子结构维护令牌桶，极高吞吐。 | 超限请求在 1ms 内立即拒绝并返回标准 429 Too Many Requests 响应。 |
| **SEC-04** | 最大并发在途连接数流控 (In-Flight) | **P0** | 限制单个 Key 或单个租户同时活跃的流式/长连接数量，防止单个失控客户端占满网关连接池资源。 | 超过配置并发上限的请求立即返回 429，释放后自动允许新连接进入。 |
| **SEC-05** | 每分钟 Token 吞吐限流 (TPM) | **P1** | 支持配置租户级/Key 级的 TPM 限制，结合滑动窗口统计短期 Token 消耗峰值，防范突发批量请求打垮配额。 | 窗口内累计 Token 超过阈值时触发 429 节流。 |
| **SEC-06** | 租户级日/月配额超额阻断 (Quota) | **P1** | 支持配置虚拟 Key 或应用团队的日度/月度总 Token 配额；当周期累计使用量耗尽时软告警或强制阻断。 | 额度耗尽后请求被拒，并在响应 Header 中给出明确超额原因与重置时间。 |
| **SEC-07** | IP 访问控制黑白名单 (CIDR) | **P1** | 支持针对管理控制台以及网关代理端口配置基于 CIDR / 单 IP 的访问控制策略。 | 非白名单 IP 发起的握手在 TCP/HTTP 层直接拒止（返回 403 Forbidden）。 |
| **SEC-08** | 请求体体积与超时防护 | **P1** | 限制单次请求 Payload 大小（默认不超过 10MB），设定上游连接握手超时（5s）与空闲读取超时（60s）。 | 防止超大畸形请求导致的 OOM 或僵尸悬挂连接吞噬系统句柄。 |
| **SEC-09** | 敏感词检测与基础正则脱敏预留 | **P2** | 在请求转发前和响应流式透传时提供基于 Aho-Corasick 或预编译 Regex 的轻量敏感词拦截/替换扩展点。 | 命中毒化词库时主动终止流式生成或替换为掩码字符。 |

## 3. 非目标边界界定 (Non-Goals)

为了确保工程实施高度聚焦于企业内部大模型网关的核心痛点，避免过度设计与无边界膨胀，本项目在当前阶段**坚决不实现**以下非目标功能：

### 🚫 Non-Goal 1: 不引入任何外部中间件依赖 (No Redis / No Kafka / No PostgreSQL)
- **范围限制**：本项目坚持**单二进制、零外部依赖**交付原则。
- **排除内容**：不依赖 Redis 进行分布式限流，不依赖 PostgreSQL/MySQL 进行数据存储，不依赖 Kafka/RabbitMQ 进行日志收集。
- **替代方案**：所有状态由网关进程内原子内存模型（Atomic / DashMap）与嵌入式 SQLite WAL 存储独立闭环完成。

### 🚫 Non-Goal 2: 不涉足底层模型推理与权重管理 (No Model Inference / Fine-tuning)
- **范围限制**：rs-gate 纯粹定位为 **API 路由、流控与安全网关**，不是推理引擎。
- **排除内容**：不包含 GPU 驱动绑定、CUDA 加速、大模型权重加载、LoRA 挂载、本地推理执行（如 llama.cpp 原生推理）或模型训练微调流水线。
- **协同方式**：企业本地模型推理交由专用的 Ollama、vLLM、Triton 或 Text Generation Inference (TGI) 承载，rs-gate 仅作为其上层反向代理统一接入点。

### 🚫 Non-Goal 3: 不实现复杂的跨厂商专有非标协议重构 (No Deep Vendor Protocol Translation)
- **范围限制**：全面拥抱主流标准的 **OpenAI 兼容协议族**。
- **排除内容**：不深度适配各家早期非标准专有 RPC 协议；不为厂商特有的极其冷门专属格式编写数十种重型 AST 语法转换器。
- **边界设定**：网关以 OpenAI Chat Completions / Embeddings 协议为黄金标准（Golden Standard），主流厂商（Azure、Anthropic 等）仅做薄适配层，不支持不遵循 HTTP/SSE 规范的私有二进制传输协议。

### 🚫 Non-Goal 4: 不构建重型企业 OA 审批中心与复杂多级部门工作流 (No Heavy Approval Workflow)
- **范围限制**：专注于网关的技术权限隔离与配额控制。
- **排除内容**：不内建繁琐的“员工发起申请 -> 部门主管审批 -> 财务总监审批 -> 自动发卡”等多级 OA 审批流引擎；不自研企业级复杂工作流引擎。
- **协同方式**：控制台提供标准 REST API，企业现有 OA 系统或脚本可通过 API 调用直接自动化开卡、分配额度与注销。

### 🚫 Non-Goal 5: 不承载实时音视频流媒体转码 (No WebRTC / Audio Stream Transcoding)
- **范围限制**：处理文本、结构化 JSON 与图片等多模态标准 HTTP 请求。
- **排除内容**：不承载全双工 WebRTC 音视频传输协议、不提供网关端音频转码与降噪重编码管道。

## 4. 非功能性需求与性能指标 (NFR & SLA Targets)

### 4.1 性能基准指标 (Performance Benchmarks)
- **网关转发附加延迟 (Proxy Overhead)**：针对非流式请求，网关内部逻辑耗时 $P99 \le 2\text{ms}$。
- **首字透传延迟 (Time to First Chunk)**：流式 SSE 场景下，上游吐出第一个 chunk 到网关投递给下游，网关内部延迟 $P99 \le 1\text{ms}$。
- **系统并发能力**：单节点（4 核 8GB）能够稳定支撑 $\ge 5,000$ 个并发活跃 SSE 流式连接，吞吐量 $\ge 10,000\text{ RPS}$。
- **资源基线占用**：
  - 空载常驻内存：$\le 30\text{MB}$。
  - 5,000 并发活跃连接峰值内存：$\le 250\text{MB}$。
  - 单二进制文件体积（包含内嵌 Web 控制台）：$\le 25\text{MB}$。

### 4.2 可靠性与数据完整性 (Reliability & Integrity)
- **审计数据不丢**：采用有界异步通道与批量提交，在系统遭遇异常断电或停机信号时触发 WAL 自动刷盘，数据丢失窗口 $< 500\text{ms}$。
- **流控精确度**：高并发竞争下，令牌桶与并发计数器原子性准确，绝对不发生超额透支击穿。
- **内存安全**：全量代码使用 Safe Rust 编写（严禁无充分论证的 `unsafe` 代码块），杜绝内存泄露、野指针与死锁。
