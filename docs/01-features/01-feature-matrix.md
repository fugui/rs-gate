## 1. 系统愿景与产品定位 (Vision & Positioning)

### 1.1 项目愿景
**rs-gate** 是一款采用 Rust 构建的高性能、低资源占用、单二进制交付的企业级内部大模型网关。它作为企业内部所有 AI 业务系统与后端高性能推理引擎（如 vLLM、SGLang、Triton、TEI、Ollama 等）及外部上游提供商之间的统一接入中枢与安全防线，解决企业大模型应用落地过程中的**凭据泄露风险**、**调用配额无序**、**异构请求并发倾斜雪崩**、**账单计量混乱**以及**运维部署沉重**等核心痛点。

### 1.2 核心价值主张 (Core Value Propositions)
1. **多协议直通中继，零协议转换损耗 (Multi-Protocol Passthrough)**：支持 `/v1/chat/completions`、`/v1/responses`（OpenAI 新一代 Agentic Responses API）、`/v1/completions`、`/v1/embeddings`、`/v1/rerank` 等多种协议端点。网关核心定位为**高性能透明中继器**而非重型转换器，对后端 vLLM/SGLang 实施原生协议直通透传，杜绝复杂跨协议 AST 转换带来的额外序列化与延迟开销。
2. **后端协议能力预先探测与界面展现 (Capability Probing & UI Visualization)**：在后端服务器添加或周期性巡检时，网关主动探测该后端节点实际支持的协议与端点类型，并在管理控制台 UI 上直观展示协议能力徽章与健康状态。
3. **多模型后端集群与加权活跃连接轮询 (Weighted Least-Active-Connections)**：支持 DeepSeek、Qwen、GLM 等多主流模型聚合；单个逻辑模型可挂接多个物理后端服务器（Backend Instances）。针对大模型请求长短极其不均（短查询几十 Token vs 深度推理长连接数十秒）的特征，独创基于**当前活跃连接数与权重比值**的动态调度算法，杜绝 GPU 节点连接堆积与 KV Cache 耗尽雪崩。
4. **两层配额防线 (日/周双层配额阻断，Daily & Weekly Quotas)**：针对企业应用提供**每日 (Daily)** 与**每周 (Weekly)** 两层 Token 配额双重保险，严格防范单日突发与单周累积滥用。
5. **极致轻量，单二进制开箱即用 (Single Binary Delivery)**：核心网关与 Web 控制台静态资源深度内嵌打包为单个可执行文件，基于 SQLite WAL 存储，无须外挂 Node.js、Redis、MySQL 或 Kafka，秒级启动。

## 2. 需求功能矩阵 (Feature Matrix)

特性优先级定义：
- **P0 (Must-Have)**：MVP 核心基石，必须在 Milestone 1~3 全部完成交付并具备生产可用性。
- **P1 (Should-Have)**：生产就绪与健壮性保障，在 Milestone 4~5 完整实施并经过压力测试验证。
- **P2 (Nice-to-Have)**：进阶与扩展特性，在核心体系稳定后作为演进增强项。

### 2.1 核心网关与路由调度领域 (Core Gateway & Routing)

| 编号 | 特性名称 | 优先级 | 功能描述与规范 | 验收指标 / 衡量标准 |
| :--- | :--- | :---: | :--- | :--- |
| **GW-01** | 多协议原生直通代理 (Passthrough) | **P0** | 原生直通支持主流大模型推理端点：`/v1/chat/completions`、`/v1/responses`（OpenAI 新一代 Responses API）、`/v1/completions`、`/v1/embeddings`、`/v1/rerank` 与 `/v1/models`；网关仅做鉴权、流控、中继透传与计量，**严禁且不做昂贵的跨协议转换**。 | 1. 客户端通过标准协议发起 Chat、Responses、Embedding 或 Rerank 请求均能透传至后端。<br>2. 网关自身处理引入额外延迟 $P99 \le 1.5\text{ms}$。 |
| **GW-02** | SSE 低延迟非阻塞流式中继 | **P0** | 针对流式响应，采用异步管道边读边写，严禁中间全量缓冲，对 `data: {...}` 事件帧及 `data: [DONE]` 实施逐 Chunk 实时透传。 | 首字透传延迟 (TTFT Overhead) $\le 2\text{ms}$，端到端 Chunk 抖动 $< 1\text{ms}$。 |
| **GW-03** | 后端协议能力预先探测 (Capability Probing) | **P0** | 当向系统添加后端服务器（如 vLLM/SGLang 实例）或执行健康探测时，网关主动预先探测该节点实际支持的协议类型与端点（Chat, Responses, Completion, Embedding, Rerank, Tokenize 等）。 | 1. 能够准确识别 vLLM/SGLang 暴露的服务能力清单。<br>2. 探测结果即时沉淀至内存状态并在前端界面呈现。 |
| **GW-04** | 多模型到后端服务器集群映射 | **P0** | 支持配置多种模型（如 DeepSeek、Qwen、GLM 等）；单个逻辑模型可挂载数个后端物理服务器实例（Backend Servers Pool），形成高可用实例组。 | 请求目标模型时，网关能准确定位其绑定的后端服务器集群并进行路由转发。 |
| **GW-05** | 基于当前活跃连接数的加权轮询调度 | **P0** | 针对同一模型下的多个后端实例，调度算法**基于当前活跃连接数而非请求计数**进行加权调度。公式：优先选择 $\frac{\text{ActiveConnections}_i}{\text{Weight}_i}$ 最小的健康后端，相同值时加权平滑轮询。 | 1. 长推理请求（如 DeepSeek-R1 数万 Token）不会在单个节点过度堆积。<br>2. 节点活跃长连接与配置权重严格成正比。 |
| **GW-06** | 流式 Token 实时提取与计量 | **P0** | 实时解析 SSE 尾部携带的 `usage` chunk（兼容 `stream_options.include_usage`），准确记录 Prompt 与 Completion Token 数并计入审计流水。 | 审计记录的 Token 消耗与推理引擎实际返回 100% 吻合。 |
| **GW-07** | 协议头清洗与追踪链路透传 | **P0** | 剥离上游敏感或冲突的 Hop-by-hop 头信息；注入统一链路追踪 ID (`x-request-id`)，透传真实客户端 IP (`X-Forwarded-For`)。 | 确保下游与后端推理引擎日志具有一致的链路追踪 ID。 |
| **GW-08** | 后端实例健康检查与动态熔断转移 (Failover) | **P1** | 周期性心跳探活后端实例；当某个后端连续超时或返回 5xx 达到阈值时，自动标记下线熔断，流量即时切至集群内其他健康实例。 | 某后端宕机后，在下一次调度时自动规避，故障恢复后经探活成功自动回加。 |
| **GW-09** | 客户端主动取消 (Abort) 实时中断传导 | **P1** | 当客户端提前断开连接时，网关立即捕获并迅速中断对后端推理服务器的长连接，防止后端 GPU 显存浪费与无意义计算。 | 客户端断连后 100ms 内向后端发出中止，释放 GPU KV Cache 计算资源。 |
| **GW-10** | 本地分词器兜底估算 (Tokenizer) | **P2** | 针对未返回 `usage` 数据的部分旧版端点或特殊直通流，引入嵌入式分词引擎（如 `tiktoken-rs`）在网关侧进行 Token 数量补偿估算。 | 缺失 usage 块时，Token 估算误差率控制在 $\pm 5\%$ 以内。 |
| **GW-11** | 上游故障静默重试与故障转移 (Upstream Silent Retry & Failover) | **P0** | 1. **错误拦截范围**：针对上游后端返回的 `5xx`（500/502/503/504）、网络连接超时/读写超时/连接重置，以及上游返回的 `429 Too Many Requests`，网关触发自动重试。<br>2. **重试机制与退避**：默认最大重试次数为 **2 次**（共最多尝试 3 次）；重试时引入退避等待时间（基础 500ms + 指数退避与随机抖动；若上游携带 `Retry-After` 头则优先遵循其等待秒数）。<br>3. **客户端无感透明**：在最大重试次数内若任一次成功，下游客户端直接获得标准正常响应，完全不感知中间故障。<br>4. **多实例智能故障转移**：若当前模型挂载多个后端，优先重试同模型下其他最轻负载健康后端（Failover）；单实例则原地退避重试。<br>5. **流式安全边界**：流式请求在首字推送前（Pre-first-chunk）支持静默重试；首字已推送后为防数据重复与格式损坏，禁止从头重试并优雅终止。 | 1. 模拟上游 500/502/503/504、超时或 429 时，网关在 2 次重试内成功恢复，客户端 100% 获得正常 200 响应与完整内容。<br>2. 多节点集群下发生故障时自动切换至次优健康节点执行。<br>3. 重试过程不重复扣减客户端 RPM 限流与 Token 配额。 |

### 2.2 流控与安全领域 (Security & Limiting)

| 编号 | 特性名称 | 优先级 | 功能描述与规范 | 验收指标 / 衡量标准 |
| :--- | :--- | :---: | :--- | :--- |
| **SEC-01** | 网关虚拟 API Key 鉴权 | **P0** | 客户端请求必须携带 `Authorization: Bearer <rs-gate-sk-xxx>`；数据库仅保存加盐 Hash 摘要（SHA-256/Argon2），禁止明文持久化。 | 非法或已撤销 Key 在 1ms 内拦截并返回标准 401 Unauthorized。 |
| **SEC-02** | 后端真实凭据物理屏蔽与隔离 | **P0** | 后端推理集群或外部服务商的真实 API Key/Token 统一由网关配置托管，外部调用方绝对不可探知后端物理凭据。 | 网关注册凭据物理隔离，响应报文绝不泄露任何后端授权凭证。 |
| **SEC-03** | 高性能内存令牌桶限流 (RPM) | **P0** | 支持为各个虚拟 Key 配置独立的每分钟请求数 (Requests Per Minute)；采用无锁原子结构维护令牌桶，极高吞吐。 | 超限请求在 1ms 内立即拒绝并返回标准 429 Too Many Requests。 |
| **SEC-04** | 最大并发在途连接数流控 (In-Flight Concurrency) | **P0** | 限制单个 Key 允许同时并发进行的在途请求/长连接上限，防止恶意或异常并发占满后端连接池。 | 达到并发阈值的请求返回 429，并在响应头告知当前并发度。 |
| **SEC-05** | 日/周双层配额超额阻断 (Daily & Weekly Quotas) | **P0** | **企业级两层限额机制**：支持针对每个 Key 或租户同时设定**每日最大 Token 额度 (Daily Limit)** 与**每周最大 Token 额度 (Weekly Limit)**。 | 1. 每日/每周累计消耗达到阈值时即刻硬阻断并返回 429。<br>2. 响应头带 `X-Quota-Daily-*` 与 `X-Quota-Weekly-*` 余量与重置倒计时。 |
| **SEC-06** | 配额周期性自动轮转重置 | **P0** | 日配额在每日 00:00:00（按系统配置时区）自动刷新；周配额在每周一 00:00:00 自动刷新重置。 | 周期到达时自动完成新周期计数轮转，无须人工干预。 |
| **SEC-07** | 每分钟 Token 吞吐限流 (TPM) | **P1** | 支持配置 Key 级别的 TPM (Tokens Per Minute) 限制，基于滑动窗口防范突发巨型 Prompt 冲击。 | 窗口累计 Token 超过阈值时触发节流 429。 |
| **SEC-08** | IP 黑白名单与访问控制 (CIDR) | **P1** | 支持对网关代理端口及管理控制台端口配置 CIDR 范围白名单。 | 非许可网段发起的连接在 TCP/HTTP 层直接拒止（返回 403 Forbidden）。 |
| **SEC-09** | 请求体体积与超时安全防线 | **P1** | 限制单次请求 Payload 体积（默认上限 10MB），限制建联超时与空闲读写超时。 | 杜绝畸形大包攻击与悬挂僵尸连接耗尽系统句柄。 |

### 2.4 系统与运维审计领域 (Ops & Audit)

| 编号 | 特性名称 | 优先级 | 功能描述与规范 | 验收指标 / 衡量标准 |
| :--- | :--- | :---: | :--- | :--- |
| **OPS-01** | 异步非阻塞审计存储管道 | **P0** | 采用 Tokio mpsc 异步有界通道解耦代理热路径与磁盘 I/O；审计事件汇聚后由后台 Worker 批量刷入 SQLite WAL 数据库。 | 磁盘写入即便发生抖动，网关代理主请求的端到端吞吐完全不受影响。 |
| **OPS-02** | SQLite 声明式迁移与自初始化 | **P0** | 数据库结构由 `migrations/` 目录中的标准 DDL 驱动；系统启动时自动检测版本并自动完成表结构创建与平滑升迁。 | 首次运行无数据库文件时，自动完成表（包含 `users`、`virtual_keys` 等 7 张核心表）、默认超管账户（`users` 表生成默认 `admin`）及基础索引自初始化。 |
| **OPS-03** | 优雅停机与连接平滑排空 (Graceful Shutdown) | **P0** | 捕获 SIGINT / SIGTERM 信号；即刻拒绝新连接，等待在途长连接正常流式完成（带最长宽限超时），关闭数据库后安全退出。 | 升级发布过程中不产生数据损坏与中断中的断裂事务。 |
| **OPS-04** | 结构化日志追踪 | **P0** | 基于 `tracing` 输出结构化日志，各请求统一绑定全局唯一 `request_id`，支持通过配置动态调整日志级别。 | 核心日志包含耗时、状态码、模型、后端实例、Token 数等关键字段。 |
| **OPS-05** | Prometheus 监控指标端点 (`/metrics`) | **P1** | 暴露符合 OpenMetrics 标准的 `/metrics` 端点，采集请求计数、活跃连接数、加权调度倾斜度、Token 速率、延迟分布 Histogram。 | 可直接被 Prometheus 抓取并在 Grafana 中展示。 |
| **OPS-06** | 标准健康检查探针 | **P1** | 提供 `/health/live`（进程存活性）与 `/health/ready`（SQLite 存储与监听就绪度）探针。 | 完美适配 Kubernetes 与轻量级容器编排体系。 |
| **OPS-07** | 历史审计数据滚动清理 (TTL) | **P1** | 支持配置日志最大留存天数（如保留 30 天）；后台低峰期定时清理过期数据并触发增量 VACUUM。 | 防止长时间运行导致 SQLite 文件单调膨胀。 |
| **OPS-08** | 单二进制跨平台静态编译交付 | **P1** | 支持 Linux (x86_64, aarch64)、macOS 及 Windows 平台独立二进制静态编译打包。 | 交付文件零系统依赖（musl/static），复制即可直接运行。 |

## 3. 非目标边界界定 (Non-Goals)

为了保证工程聚焦于企业内部大模型网关的核心痛点，杜绝过度设计，本项目在当前阶段**坚决不实现**以下非目标特性：

### 🚫 Non-Goal 1: 坚决不引入外部中间件依赖 (No External Middleware: Redis / Kafka / Postgres)
- **范围限制**：坚守**单二进制、零外部组件依赖**的架构红线。
- **排除内容**：不依赖 Redis 实现分布式缓存或限流，不依赖 Kafka/RabbitMQ 传递日志，不依赖 PostgreSQL/MySQL 存储数据。
- **落地方案**：所有流控与活跃连接计数在网关进程内原子内存模型（`Atomic*`）闭环；持久化审计与元数据完全由嵌入式 SQLite WAL 承载。

### 🚫 Non-Goal 2: 绝不进行跨厂商复杂非标协议的深度转译 (No Protocol Translation)
- **范围限制**：核心采用**协议直通 (Passthrough)** 机制。
- **排除内容**：不对请求体或响应体进行复杂的跨厂商 AST 语义转译（例如不做 Anthropic Claude XML 与 OpenAI 格式之间的深度双向语法树重构，也不做专有私有 RPC 协议转译）。
- **落地方案**：客户端协议直接面向后端推理引擎（vLLM / SGLang / TEI 原生已支持标准 OpenAI 协议及扩展端点），网关只对数据流进行流式透传、鉴权拦截与计量分析。

### 🚫 Non-Goal 3: 不涉足底层模型推理与权重生命周期管理 (No Local Inference Engine)
- **范围限制**：rs-gate 纯粹定位为 **API 接入、路由与安全治理网关**，而非推理运行时。
- **排除内容**：网关本身不绑定 CUDA/GPU 驱动，不加载模型权重，不自研推理加速库，不集成 llama.cpp 原生推理代码。
- **协同方式**：企业算力统一由 vLLM、SGLang、Triton、Ollama 等专业推理后端承担，网关作为反向代理与集群调度器。

### 🚫 Non-Goal 4: 不构建重型企业多级审批流与 OA 协同引擎 (No Heavy Approval Workflow)
- **范围限制**：聚焦于网关层面的技术鉴权、模型隔离与日/周限额。
- **排除内容**：不内置“员工申请 -> 主管审批 -> 财务审批 -> 自动分发”等多级企业 OA 流程；不自建庞大工作流引擎。
- **协同方式**：控制台提供标准 REST API，外部既有企业系统（飞书、钉钉、OA）可直接调用网关 API 实现自动开卡与额度同步。

### 🚫 Non-Goal 5: 不承载实时音视频流媒体转码 (No Audio/Video Transcoding)
- **范围限制**：支持文本、结构化数据、向量嵌入及标准图片多模态。
- **排除内容**：不承载全双工 WebRTC 流媒体转码及网关端语音降噪重编码。

## 4. 关键调度与流控算法设计规范 (Key Algorithms & Mechanics)

### 4.1 加权最小活跃连接数轮询算法 (Weighted Least-Active-Connections)
由于 LLM 请求负载具有极强的非对称性（例如一个问答仅耗时 200ms，而一个 DeepSeek-R1 深度思考推理长连接可能持续占用 GPU 显存 60 秒），若采用常规轮询或请求次数轮询，极易导致长请求聚集在少数节点而引发显存 OOM 或请求阻塞。

网关采用基于**当前实时在途长连接数**的加权调度策略：
1. **指标定义**：
   - 设后端实例 $i$ 的当前活跃长连接数为 $C_i$（通过原子操作 `fetch_add` / `fetch_sub` 精准实时追踪）。
   - 设后端实例 $i$ 的配置权重为 $W_i$（正整数，默认 10）。
   - 定义节点当前负载比率：
     $$\text{LoadRatio}_i = \frac{C_i}{W_i}$$
2. **选路规则**：
   - 每次接收到新的请求时，过滤出当前健康（Healthy）的后端实例集合。
   - 优先选择 $\text{LoadRatio}_i$ 最小的实例。
   - 若存在多个实例的 $\text{LoadRatio}$ 相同，则在这些候选节点间进行平滑轮询（Round-Robin）。
3. **连接生命周期**：
   - 请求分发给后端实例 $i$ 前：`$C_i$.fetch_add(1)`；
   - 响应流结束（或客户端中途断开/上游报错）时：`$C_i$.fetch_sub(1)`。

### 4.2 后端能力预先探测机制 (Backend Capability Probing)
1. **探测触发点**：
   - 管理员在控制台新增/修改后端服务器配置时立即触发探测；
   - 后台健康检查探针按配置周期（如每 15 秒）在探活心跳中执行能力探测。
2. **探测协议矩阵**：
   - **Chat 端点**：探活探测 `/v1/chat/completions`（通过轻量探测或预检）。
   - **Responses 端点**：探活探测 `/v1/responses`（OpenAI 新一代 Agentic Responses API）。
   - **Completions 端点**：探活探测 `/v1/completions`。
   - **Embeddings 端点**：探活探测 `/v1/embeddings`。
   - **Rerank 端点**：探活探测 `/v1/rerank`。
   - **元数据与模型列表**：读取 `/v1/models`，解析当前节点加载的模型 ID 与能力标签。
3. **状态沉淀与展示**：
   - 探测结果以位掩码或标签集合（`HashSet<ProtocolType>`）缓存在内存后端实例结构中。
   - 管理控制台通过 `/api/admin/backends` 获取并直观展示协议徽章列表。

### 4.3 租户级日/周两层配额防线 (Daily & Weekly Quotas)
为杜绝配额被快速刷光或长周期无法纠偏，系统实行日与周两级配额管理：
1. **配额维度**：
   - **Daily Quota ($Q_{\text{day}}$)**：单个自然日内的 Token 消耗总上限。
   - **Weekly Quota ($Q_{\text{week}}$)**：单自然周内的 Token 消耗总上限。
2. **拦截判定逻辑**：
   - 请求前快速比对当前统计周期内的已使用量：
     - 若 $\text{Used}_{\text{day}} \ge Q_{\text{day}}$：立即拒绝，返回 HTTP 429，并在响应头附带 `X-Quota-Type: daily`，`X-Quota-Reset: <今日午夜时间戳>`。
     - 若 $\text{Used}_{\text{week}} \ge Q_{\text{week}}$：立即拒绝，返回 HTTP 429，并在响应头附带 `X-Quota-Type: weekly`，`X-Quota-Reset: <本周日午夜时间戳>`。
3. **重置周期**：
   - **日重置**：每日本地时区 00:00:00 自动开启新日计数。
   - **周重置**：每周一本地时区 00:00:00 自动开启新周计数。
   - **人工即时重置**：管理员可在控制台对指定 Key 一键重置“今日使用量”或“本周使用量”。

### 4.4 上游静默重试与自适应退避调度 (Upstream Silent Retry & Adaptive Backoff)
1. **触发与过滤判定**：
   - **重试范围**：上游 HTTP 状态码 $\in \{500, 502, 503, 504, 429\}$ 或网络连接异常（`ConnectTimeout`, `ReadTimeout`, `ConnectionReset`, `BrokenPipe`）。
   - **硬阻断（绝不重试）**：客户端自身输入引起的 4xx 状态码（400, 401, 403, 404, 422），直接透传给客户端。
2. **自适应等待时间计算 (Adaptive Backoff with Full Jitter)**：
   - 若上游响应头包含合法 `Retry-After: <seconds>`，重试等待时间优先取该值（上限 10 秒）；
   - 否则按带随机抖动的指数退避计算：
     $$\text{WaitTime} = \min\left(\text{MaxBackoff},\, \text{UniformRandom}(0,\, \text{BaseInterval} \times 2^{\text{attempt}})\right)$$
     其中默认 $\text{BaseInterval} = 500\text{ms}$，$\text{MaxBackoff} = 5000\text{ms}$，有效瓦解瞬时重试并发风暴。
3. **选路转移与单后端退避**：
   - 设当前候选健康节点集合为 $\mathcal{H}$。
   - 发生重试时，将本次失败的节点从临时局部重试候选集排除，重新通过加权最小活跃连接算法（WLAC）选取下一个最优健康实例（Failover）；
   - 若模型仅配置 1 个后端或所有可用节点均已尝试过，则在原节点等待退避时间后原地重试，直至达到最大重试次数（默认 2 次，即总共最多尝试 3 次）。
4. **配额与连接生命周期保证**：
   - 重试切换后端时，立即释放失败节点的 `ActiveConnectionGuard`，再为重试目标申领新的 Guard；
   - 客户端虚拟 Key 的 RPM 令牌桶与日/周配额仅在最终成功（或最终失败）时进行唯一定额审计结算，绝不因内部重试发生重复扣费。

## 5. 非功能性需求与性能指标 (NFR & SLA Targets)

### 5.1 性能基准指标 (Performance Benchmarks)
- **网关转发附加延迟 (Proxy Overhead)**：针对非流式直通请求，网关内部逻辑耗时 $P99 \le 1.5\text{ms}$。
- **首字透传延迟 (Time to First Chunk)**：流式 SSE 场景下，上游吐出首个 chunk 到网关投递给下游，网关内部额外延迟 $P99 \le 1\text{ms}$。
- **高并发支撑能力**：单节点（4 核 8GB）能够稳定支撑 $\ge 5,000$ 个并发活跃长连接，吞吐量 $\ge 10,000\text{ RPS}$。
- **资源基线占用**：
  - 空载常驻内存：$\le 30\text{MB}$。
  - 5,000 并发活跃长连接峰值内存：$\le 250\text{MB}$。
  - 单二进制文件体积（含内嵌 Web 控制台）：$\le 25\text{MB}$。

### 5.2 可靠性与数据完整性 (Reliability & Integrity)
- **审计数据不丢**：采用 Tokio 有界通道与批量落盘，在系统遭遇异常断电或退出信号时触发 WAL 自动刷盘，数据丢失窗口 $< 500\text{ms}$。
- **流控与调度原子性**：高并发竞争下，活跃连接计数器与令牌桶操作完全采用原子指令保证绝对准确，不发生并发击穿。
- **内存安全**：全量核心业务代码使用 Safe Rust 编写，杜绝野指针、内存泄漏与死锁。

## 6. 阶段一结论与后续演进衔接

本特性清单与需求范围界定规范（`01-feature-matrix.md`）已全面吸收反馈完成更新：
1. **多协议直通**：支持 Chat、Responses、Completions、Embeddings、Rerank 等端点直通后端 vLLM/SGLang，不进行昂贵的跨协议转换；
2. **能力预探测与展示**：网关自动探测后端实际支持的协议类型并在控制台呈现徽章；
3. **多模型后端集群与加权活跃连接调度**：支持 DeepSeek、Qwen、GLM 等多模型，采用加权最小活跃长连接轮询，解决大模型请求长短不均的倾斜问题；
4. **两层配额防线**：正式确立日配额 (Daily) + 周配额 (Weekly) 严格限额与重置策略；
5. **上游故障静默重试与故障转移**：针对上游 5xx/429/网络超时增加自动重试（默认 2 次）与自适应退避等待，多实例优先故障转移，流式首字前静默重试，实现下游客户端对上游抖动完全无感。
